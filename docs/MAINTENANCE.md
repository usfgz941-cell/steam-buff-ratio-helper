# 维护与同步规则

## 两个系统的职责

### GitHub：代码与版本权威来源

放这里：

- `.user.js` 安装脚本；
- 版本号与更新地址；
- 安装说明；
- 算法说明；
- 数据模型；
- 排错文档；
- 安全边界；
- Changelog。

任何“脚本现在到底怎么工作”的问题，以 GitHub 当前主分支为准。

### Notion：个人运行手册与验证记录

放这里：

- 实际使用参数；
- 某次真实 Steam 测试结果；
- 推荐价是否合理的反馈；
- 个人决策规则；
- 待优化问题；
- 版本验收状态。

Notion 不复制完整源码，避免两份代码失同步。

## 推荐更新顺序

### 修改代码 / 算法

1. GitHub 更新代码；
2. GitHub 更新 `CHANGELOG.md` 与相关文档；
3. Tampermonkey 实机测试；
4. 把测试结论同步到 Notion。

### 只记录真实使用结果

1. 先写 Notion；
2. 如果发现需要修改通用算法，再回到 GitHub 修改代码 / 文档。

## 版本验收

每次发布新版本，Notion 应至少记录：

```text
版本：
测试日期：
Steam 钱包货币：
CSV 导入：通过 / 失败
成本匹配：通过 / 失败
您收款读取：通过 / 失败
实时比例：通过 / 失败
市场卖盘：通过 / 失败
推荐价：合理 / 需调整
已知问题：
```

## 为什么这样分工

最容易失控的不是代码量，而是“同一个规则在 GitHub、Notion、聊天记录里出现三个版本”。

因此：

> GitHub 管规则与实现，Notion 管真实使用事实与决策。

这样后续优化推荐价时，可以从 Notion 的真实案例出发，再回到 GitHub 修改通用算法，而不是直接凭印象改代码。
