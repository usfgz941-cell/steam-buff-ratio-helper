# 外部方案调研与查漏补缺（2026-08）

本文件记录 V0.1.x 阶段对 Steam 官方前端实现、成熟社区脚本以及当前项目架构的对照审计。

## 结论先行

当前项目已经能够覆盖“导入 BUFF 成本 → Steam 出售窗口实时算比例 → 给出三档建议”的主链路，但距离稳定长期使用还缺四个关键环节：

1. **手续费必须以 Steam 钱包元数据和 Steam 自己的取整规则为准**，不能把“15%”当作统一公式。
2. **汇率口径必须明确标注**：NBU 中间价只是参考，不一定等于用户实际把人民币换成 UAH Steam 余额的真实成本。
3. **推荐挂价需要估计等待时间**：核心是“多让一个价位，能换来多少成交速度”，而不是简单看最低价或堆更多指标。
4. **当前分片加载器属于过渡架构**：虽有 SHA-256 校验，但仍依赖运行时从 GitHub 拉取多个分片并执行远程代码；正式版应改成单文件、可审计、可离线回退的构建产物。

## 参考方案

### Steam 前端实现（SteamTracking 镜像）

Steam 社区市场前端的 `economy_common.js` 暴露了以下关键逻辑：

- `wallet_market_minimum`
- `wallet_currency_increment`
- `wallet_publisher_fee_percent_default`
- `wallet_fee_percent`
- `ToValidMarketPrice`
- `CalculateFee`
- `GetTotalWithFees`
- `GetItemPriceFromTotal`

因此，精确的“买家支付 ↔ 您收款”关系是：先按当前钱包货币的最小金额和价格增量归一化，再分别计算发行商手续费和 Steam 手续费，最后反推基础金额。低价整数货币（包括 UAH）尤其容易因最低手续费和取整产生与简单除以 1.15 不一致的结果。

参考：

- https://github.com/SteamTracking/SteamTracking/blob/master/steamcommunity.com/public/javascript/economy_common.js
- https://github.com/SteamTracking/SteamTracking/blob/master/steamcommunity.com/public/javascript/economy.js
- https://github.com/SteamTracking/SteamTracking/blob/master/steamcommunity.com/public/javascript/economy_v2.js

### Steam Economy Enhancer

成熟社区脚本 Steam Economy Enhancer 值得借鉴的不是“自动卖出”，而是工程稳定性：

- 从 `g_rgWalletInfo` 读取当前钱包币种和手续费元数据；
- 对 UAH、JPY、TWD 等整数货币做专门取整处理；
- 市场请求排队、延迟、缓存；
- 遇到 403 / 429 等错误后退避并停止连续请求；
- 可配置忽略最低异常卖单数量、价格偏移和历史窗口；
- 持久缓存与会话缓存分离。

参考：

- https://github.com/Nuklon/Steam-Economy-Enhancer

### Tampermonkey 官方文档

需要遵循的发布原则：

- `@downloadURL` 与 `@updateURL` 固定指向可审计的安装文件；
- 尽量减少 `@connect` 范围；
- 不请求 Cookie、密码或 API Key；
- 依赖应固定版本，正式分发文件不应在运行时拼接并执行不透明远程代码。

参考：

- https://www.tampermonkey.net/documentation.php

## 推荐价的因果机制

候选价格 `p` 影响两个核心结果：

1. **到账金额**：价格越高，售出后余额越多，实际比例越低；
2. **排队位置**：价格越高，通常排在更多卖单后面，等待时间越长，期间价格下跌或供给增加的风险也越高。

因此推荐价不应直接等于“最低卖价 + 1”，而应在满足比例底线的候选价格中，最大化：

```text
预期效用(p)
= 预计到账价值(p)
- 时间成本 × 预计等待时间(p)
- 风险偏好 × 等待期间的价格下跌风险(p)
```

对第一版而言，不必假装能精确预测；只需做到：

- 明确展示排队数量；
- 用近期销量估计等待区间；
- 给快速 / 均衡 / 耐心三种不同时间成本权重；
- 数据不足时显示“建议置信度低”。

## 更关键但容易忽略的问题：比例的汇率基准

所谓 `0.65` 或 `0.70`，本质是：

```text
人民币现金成本 / 人民币等价的 Steam 钱包到账价值
```

如果使用 NBU 中间价，就只能称为“按 NBU 参考汇率的比例”；它不一定等于用户实际购买 UAH、充值、消费或未来处置余额时的真实汇率。

因此后续 UI 应至少提供三种模式：

1. **实际成本汇率（推荐）**：用户输入自己真实的 CNY→UAH 获取成本；
2. **NBU 参考汇率**：自动更新，适合统一比较；
3. **Steam 隐含汇率**：仅作为观察值，不与现实可兑换汇率混为一谈。

面板必须同时显示模式和更新时间，不能只显示一个看似精确的比例。
